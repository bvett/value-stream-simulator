## Purpose / Big Picture

An individual running the value-stream demo will be able to submit one set of tasks and many models to an HTTP service, see each model complete, and use the existing Python result viewers without changing the meaning of their plots. When no remote URL is configured, `SimulationRunner` will start a loopback HTTP server, use it, and close it. A later browser application can use the same documented job API. Run `python src/examples/demo.py` after implementation to observe the local service and existing plots, or start the service separately and point the demo at it with `VALUE_STREAM_SERVICE_URL`.

## Surprises & Discoveries

- Observation: `SimulationRunner.execute` currently invokes `Simulation.execute` once per model and returns a list of Python `SimulationResult` objects. `ResultViewer` and `MetadataViewer` traverse those objects, including event and resource metadata. Evidence: `src/value_stream/client/simulation_runner.py`, `src/value_stream/client/views/result_viewer.py`, and `src/value_stream/client/views/metadata_viewer.py`. The HTTP client must reconstruct those same types.
- Observation: QA, toolchain, and resource selection use Python's module-level `random`; tasks and resources receive UUIDs. Evidence: `src/value_stream/resources/qa_tester.py`, `src/value_stream/resources/toolchain.py`, and `src/value_stream/workflow/pool_manager.py`. Separate model processes are needed for concurrent seeded runs without one model changing another's random stream.
- Observation: `Model` can hold finite `ResourcePool` objects or concrete resource collections. Evidence: `src/value_stream/simulation/model.py` and `src/value_stream/resources/resource_pool.py`. The wire adapter must describe pools explicitly and reject an unlimited pool in version 1.
- Observation: The sandbox rejected loopback socket binding, while the approved local integration tests and the temporary Uvicorn server passed with loopback access. Evidence: the first runner test raised `PermissionError` at socket bind; `tests/integration/test_local_runner.py` then passed with escalation. Loopback checks require that permission in this environment.
- Observation: Docker Desktop was enabled after the initial packaging work. Its daemon socket was unavailable until Docker Desktop started, and the Codex app sandbox denied socket access even then; approved Docker commands reached the engine. Evidence: `docker version` returned Docker Desktop 4.91.0 and Engine 29.8.0 after escalation; the image built and ran successfully.
- Observation: FastAPI's current test client emitted Starlette/HTTPX deprecation warnings; the feature tests still passed. Evidence: the final repository coverage run passed 148 tests with three warnings. Treat these as dependency maintenance, not service failures.

## Decision Log

- Decision: Version 1 has a Python HTTP client and no browser UI; the service uses `DefaultSimulationPolicy`. Rationale: This preserves the current demo while leaving a portable API for the next phase. Date/Author: 2026-09-15, user.
- Decision: One job accepts shared tasks and a batch of models. Model runs may finish out of order, but the Python return list follows submission order. Rationale: Large batches can progress without keeping an HTTP submission request open. Date/Author: 2026-09-15, user.
- Decision: The API exposes each result as it finishes and continues after individual model failures. The runner raises a batch error with successful results and model-indexed errors after a partial failure. Rationale: Callers can inspect partial outcomes without passing error objects to existing viewers. Date/Author: 2026-09-15, user.
- Decision: An optional job seed determines an independent random stream per model. Rationale: Results must be repeatable despite concurrent scheduling. Date/Author: 2026-09-15, user.
- Decision: Use FastAPI for request validation and OpenAPI 3.1 output, Uvicorn for the HTTP server, HTTPX for the Python client, and a bounded set of standard-library subprocesses for model execution. Rationale: The HTTP layer remains responsive; each child has isolated random state; a child can be stopped without corrupting a reusable worker pool. Date/Author: 2026-09-15, Codex design choice.
- Decision: Keep Uvicorn as the ASGI HTTP server for version 1. `asyncio` supplies event-loop primitives underneath a web server; the `websockets` package implements the WebSocket protocol, which is not needed for the version 1 polling API. Uvicorn serves FastAPI's HTTP routes, handles server startup/shutdown, and can also serve WebSocket routes if a later UI needs them. Rationale: This avoids building HTTP parsing, connection handling, and application lifecycle code around lower-level networking primitives. Date/Author: 2026-09-15, Codex clarification after user review.
- Decision: Treat the OpenAPI 3.1 HTTP/JSON contract as the public interface. Python object reconstruction belongs only to the Python client; a browser client may use standard `fetch` or a generated client in its own language. Rationale: A future web UI must not depend on importing `value_stream`. Date/Author: 2026-09-15, Codex clarification after user review.
- Decision: Add a CI drift check between simulation constructor/configuration fields and wire schemas, plus behavioral round-trip tests and a reviewed OpenAPI artifact. Rationale: A new defaulted `Model` parameter could otherwise be silently omitted by the adapter. Date/Author: 2026-09-15, Codex clarification after user review.
- Decision: Version 1 uses one HTTP server process and an in-memory job store behind a small storage interface. A future shared store will be needed before multiple HTTP server processes can serve the same job IDs. Rationale: Jobs need not survive restarts now, while the API and scheduler can later use shared storage. Date/Author: 2026-09-15, Codex design choice.
- Decision: Bound serialized worker output inside each child before writing it to stdout, and allow a small error envelope above the numerical result limit. Rationale: Excess model metadata becomes a model-indexed error without filling the parent process's output buffer. Date/Author: 2026-09-15, Codex implementation refinement.
- Decision: Release completed scheduler futures and give the HTTP client an overall wait limit in addition to per-request timeouts. Rationale: Long-lived demo servers must not retain completed request payloads or poll a broken job forever. Date/Author: 2026-09-15, Codex implementation refinement.
- Decision: Gate the number of active jobs separately from the number of model workers, dispatching queued jobs only when an active job finishes. Rationale: The configurable active-job and queued-job limits must govern actual execution, not only admission. Date/Author: 2026-09-15, Codex implementation refinement.
- Decision: Return a documented error envelope for unexpected HTTP failures and cancel a newly created job if scheduling fails. Rationale: A caller gets a stable error contract and the failed submission does not retain active work. Date/Author: 2026-09-15, Codex implementation refinement.
- Decision: Validate the shape and index of each terminal model outcome and reject incomplete job results in the Python client. Rationale: A malformed service response must not silently return fewer `SimulationResult` objects than submitted models. Date/Author: 2026-09-15, Codex implementation refinement.

## Context and Orientation

All paths below are relative to `~/dev/value-stream`. `src/value_stream/simulation/simulation.py` runs one model against a list of `Task` objects and returns a `SimulationResult`, which contains a summary and metadata. `src/value_stream/simulation/model.py` defines the model's developers, QA testers, toolchain, cadence, and support settings. `src/value_stream/resources/resource_pool.py` creates homogeneous QA or toolchain resources from a finite limit and constructor settings. `src/value_stream/client/simulation_runner.py` is the existing caller-facing wrapper. `src/examples/demo.py` and the viewers under `src/value_stream/client/views/` are compatibility consumers. Tests are under `tests/unit/`; add service/client integration tests under `tests/integration/`.

A job is a submitted batch that has a stable ID. A model outcome is either one successful result or one structured error, tagged by the model's zero-based submission index. A cursor is a monotonically increasing completion number used to fetch outcomes once without depending on completion order. An adapter converts current Python objects to explicit JSON fields and back; it must never serialize arbitrary object internals or accept pickled Python objects over HTTP. A storage interface is a small set of methods for creating, updating, reading, and expiring jobs; the first implementation keeps bounded data in memory. A worker is a child Python process running one model. An admission limit rejects a job before work starts when it would exceed configured capacity.

The request must contain at least one task and one model. Its optional `seed` is a nonnegative integer. Task fields are finite JSON numbers with the constraints already enforced by `Task` (`initial_value` and `story_points` nonnegative, `depreciation_rate` between zero and one, and `creation_sim_t` nonnegative). A developer descriptor has `name` and positive `efficiency`. A QA descriptor has `time_cost`, `failure_rate`, and `failure_cost`; a toolchain descriptor has `deployment_duration` and `failure_rate`. Pool descriptors add a positive finite `limit`, whereas list descriptors enumerate individual resources. Resource pool inputs must not carry a Python class name. Reject non-finite numbers and negative durations before starting a job.

## Plan of Work

Milestone 1 produces the wire contract and adapters. Add `src/value_stream/service/schemas.py` with Pydantic request, result, job, and error models, and `src/value_stream/service/codec.py` with explicit converters between those models and `Task`, `Model`, `SimulationResult`, `TaskEvent`, and `ResourceMetadata`. Add `src/value_stream/client/web/codec.py` only if the service codec would otherwise import the client; prefer a shared codec in the service package without an HTTP dependency. A task request carries `initial_value`, `story_points`, `depreciation_rate`, `task_name`, `creation_sim_t`, and `task_type`; running history is not submitted. A model request carries `developer_team` as individual developer descriptors, `deployment_cadence`, `qa_testers` and `toolchain_pool` as either finite pool descriptors or finite concrete-resource lists, `support_interval`, and `support_task_story_points`. A result carries `model_index`, a model description, summary fields, all task-event fields, and all resource-metadata fields. Encode enums as their string values and UUIDs as canonical strings; reconstruct enum and UUID Python types for current consumers. Keep the originally submitted `Model` object in both reconstructed `SummaryResult.model` and `SimulationMetadata.model` so existing caller references remain stable. Reject unsupported subclasses and unlimited pools with validation errors. Test round trips and viewer construction before adding HTTP.

Add `tests/unit/service/test_contract_alignment.py` as a build-time guard. It compares the named parameters of `Model.__init__` with the named configuration fields represented by `ModelRequest`, following the explicit mapping for nested resource descriptors. It also constructs a model with distinctive non-default values and compares its stored configuration attributes with the fields the codec emits; `team_size` is an explicitly allowed derived attribute. Apply the same signature and round-trip checks to `Task`, `Developer`, `QATester`, and `Toolchain`. Check output alignment too: compare fields populated by `SummaryResult`, `SimulationMetadata`, `TaskEvent`, and `ResourceMetadata` with their result DTO fields, allowing deliberate exclusions such as duplicate `Model` references. If a new field appears, the test must fail until the wire schema and both codec directions are updated, or until a documented reason says the field is derived or intentionally server-only. Keep a checked-in generated OpenAPI 3.1 artifact under `src/value_stream/service/openapi.json` and compare canonical, key-sorted JSON with the application-generated contract in CI so API changes are visible in review. This check cannot infer whether an attribute changes simulation behavior; add a seeded service-versus-direct-simulation behavior test with non-default model settings, and require a reviewer to decide whether any new behavioral field needs wire representation or an API version change.

Milestone 2 produces a usable job service. Add `src/value_stream/service/app.py` with a FastAPI application factory, `src/value_stream/service/job_store.py` with a lock-protected in-memory store and a replaceable storage protocol, `src/value_stream/service/scheduler.py` with a global capacity gate and bounded worker slots, `src/value_stream/service/worker.py` as an importable child entry point, and `src/value_stream/service/settings.py` for validated configuration. The worker receives one validated model and the shared tasks as JSON through standard input, sets its own random seed derived deterministically from the job seed and model index, constructs fresh Python objects, calls `Simulation.execute(..., policy=DefaultSimulationPolicy())`, and writes one bounded JSON outcome to standard output. Without a seed, let each child choose its independent random state. The scheduler launches workers with `sys.executable -m value_stream.service.worker`, enforces a per-model wall-time limit, captures a failure or timeout by model index, and starts the next queued model. Use subprocess `communicate` and terminate/kill only that child's process on timeout or cancellation. Never put simulation work inside an HTTP request handler. A completed outcome becomes visible immediately. The server process owns one store and one scheduler; launch Uvicorn with one server worker in version 1 because separate server workers do not share the in-memory store.

For a supplied seed, compute the child seed as the unsigned integer represented by the first eight bytes of SHA-256 over the UTF-8 string `"<job-seed>:<model-index>"`, then call `random.seed(child_seed)` inside that child before reconstructing resources. Use the same rule on every platform. This guarantees that a model's numerical simulation outcome does not depend on when its child starts. Generated UUID values are identity metadata and are not promised to repeat with the seed; assertions for seeded behavior should compare completion times, delivered values, losses, event timing/status, and resource totals rather than UUIDs.

The HTTP routes are `POST /v1/simulation-jobs` returning 202 with `job_id` and status URL; `GET /v1/simulation-jobs/{job_id}` returning job state and per-model counts; `GET /v1/simulation-jobs/{job_id}/outcomes?after=<cursor>` returning completed outcomes with their completion cursor; and `DELETE /v1/simulation-jobs/{job_id}` requesting cancellation. A health route at `GET /health` returns 200. FastAPI serves `/openapi.json`; verify it says OpenAPI 3.1 and includes success and error schemas for every route. Job states are `queued`, `running`, `completed`, `completed_with_errors`, and `cancelled`. Model states are `queued`, `running`, `succeeded`, `failed`, and `cancelled`. An individual model exception becomes `{model_index, code, message}`; do not expose a traceback in HTTP responses. Return 400 or 422 for invalid input, 413 for excessive body size, 429 for full job admission capacity, 404 for unknown or expired IDs, and 500 only for unexpected server failures. Terminal jobs expire after one hour by default. Cancel queued models immediately and stop running child processes; preserve outcomes already finished. A cancelled job stays readable until expiry.

The status response contains `job_id`, `status`, `total_models`, `queued_models`, `running_models`, `succeeded_models`, `failed_models`, `cancelled_models`, and `last_cursor`. The outcome page contains `outcomes` and `next_cursor`; each outcome contains `cursor`, `model_index`, `status`, and exactly one of `result` or `error` for succeeded or failed models. Increment the cursor atomically whenever a model becomes terminal. `after=0` means all completed outcomes; later calls return only outcomes whose cursor is greater than `after`, in cursor order. A terminal status means there will be no more outcomes. Use an error envelope `{code, message, details}` for request-level errors, with `details` omitted or a JSON object; a model error also contains `model_index`. Define all of these shapes as OpenAPI response models, including 202, 200, 404, 413, 422, and 429 responses.

Milestone 3 produces the Python client and local lifecycle. Add `src/value_stream/client/web/client.py` using an HTTPX client with finite connection/read timeouts. It submits the batch, polls status and outcomes by cursor, updates the caller's `tqdm` progress bar once per terminal model outcome, reconstructs successful `SimulationResult` objects using the original model at each index, and raises `BatchSimulationError` with `successful_results: list[tuple[int, SimulationResult]]` and `errors: dict[int, ModelError]` when any model fails. A fully successful call returns `list[SimulationResult]` in index order. Add `src/value_stream/client/web/local_service.py` with a loopback Uvicorn server in a background thread, a process-wide reference count, a bounded readiness wait, and orderly shutdown; use port 0 so a free loopback port is chosen. Change `SimulationRunner.__init__(service_url: str | None = None)` to use its argument, then `VALUE_STREAM_SERVICE_URL`, then the managed local server. Add `close()` and context-manager support; release the local server when the final owning runner closes, and add a process-exit cleanup fallback for current callers that do not call `close()`. Keep `task_states()` and the current `execute` arguments; add an optional `seed` argument. Reject a non-default policy explicitly in version 1. Update `src/examples/demo.py` to use the runner as a context manager and show how to set the remote URL above the runner.

Milestone 4 produces deployment and broad validation. Add `Dockerfile` and `.dockerignore` at repository root, using a Python 3.11-or-newer base image, installing the package, and running one Uvicorn server worker. Bind the standalone Docker service to `0.0.0.0` within the container; the managed local service binds only to loopback. Document environment settings and the service command in `README.md`. Add tests for schema rejection, a fast two-model API job, out-of-order completion, a failed model beside a successful one, deterministic seeded outcomes, timeout/cancellation, cursor polling without duplicates, job expiry, capacity limits, local startup/close, remote connection errors, and existing viewer data compatibility. Verify the full suite and run a small end-to-end job over a real loopback socket. Keep plotting tests headless; inspect viewer data rather than opening windows.

The later browser UI can be served from the same origin; if it is hosted on another origin, configure cross-origin access explicitly when that UI is built. ## Interfaces and Dependencies

Add `fastapi>=0.99`, `uvicorn`, and `httpx` to `pyproject.toml`; add compatible pinned entries to `requirements.txt` when implementation fixes versions. Pydantic is already a project dependency. FastAPI produces OpenAPI 3.1 from request and response models, Uvicorn serves the application, HTTPX supplies finite timeout control, and standard-library `subprocess` gives each model an isolated, terminable process. Check the installed versions and generated `/openapi.json` during implementation rather than assuming a transitive dependency version. Do not use FastAPI's background-task facility for CPU-heavy simulation work.

In `src/value_stream/service/app.py`, expose `create_app(settings: ServiceSettings | None = None, store: JobStore | None = None) -> FastAPI`. In `src/value_stream/service/codec.py`, expose `encode_request(tasks: list[Task], models: list[Model], seed: int | None) -> JobRequest`, `decode_model(...) -> Model`, `decode_tasks(...) -> list[Task]`, `encode_result(result: SimulationResult, model_index: int) -> ModelSuccess`, and `decode_result(success: ModelSuccess, original_model: Model) -> SimulationResult`. In `src/value_stream/client/web/client.py`, expose `WebSimulationClient.execute(tasks, models, pbar=None, seed=None) -> list[SimulationResult]`. Keep policy validation in `SimulationRunner` rather than the HTTP API, because version 1 has only the default policy. Define `BatchSimulationError` in `src/value_stream/client/web/errors.py` and export it from `src/value_stream/client/web/__init__.py`.

Initial configurable defaults are 1,000 tasks per job, 100 models per job, 2 MiB request body, four active jobs with four additional queued jobs, at most `min(4, os.cpu_count() or 1)` active model workers, 120 seconds per model, 8 MiB per model outcome, 64 MiB total outcomes per job, 64 retained jobs, 256 MiB total retained outcome bytes, and one hour retention after a terminal state. Admission rejects a new job if any active, queued, retained-count, or retained-byte limit would be exceeded; existing jobs remain readable until expiry. Prune expired jobs on submission and read. Validate positive settings at startup and expose environment overrides prefixed `VALUE_STREAM_` such as `VALUE_STREAM_MAX_TASKS`, `VALUE_STREAM_MAX_MODELS`, and `VALUE_STREAM_MAX_MODEL_SECONDS`. Treat these as demonstration defaults: tests should override them with smaller values to prove rejection and timeout paths. If profiling of the demo proves a default too low, record evidence and revise it in the plan and spec before release.

## Validation and Acceptance

The feature is accepted when `SimulationRunner()` with no configured URL starts a loopback service and `execute` returns normal `SimulationResult` objects; closing the last runner releases the service. The existing `ResultViewer` and `MetadataViewer` can consume results from the HTTP path and produce their expected data frames. A remote URL supplied in the runner constructor or `VALUE_STREAM_SERVICE_URL` uses that service and does not start a local one. A batch with many models returns a 202 job ID quickly; status remains readable while models run; each completed model outcome is independently retrievable; and the final Python results are in submission order. An invalid model reports its index as an error without preventing valid models from finishing. A seeded run repeated with identical submitted inputs yields identical numerical results even when completion timing differs. A client using only HTTP and JSON can submit and retrieve a job without importing Python package classes. A new `Model` configuration parameter makes the contract-alignment check fail until the adapter decision is explicit. Excess jobs, payloads, and timed-out models receive documented errors rather than exhausting the service. A Docker container can serve `/health` and `/openapi.json`. The full repository test command succeeds and produces `coverage.xml`.

## Idempotence and Recovery

Keep all new files additive until the HTTP path passes its own tests. Only then replace runner internals; its public result type remains intact. Re-running tests or restarting the service may lose in-memory jobs, which is expected for version 1. If a worker dies, record an indexed failure and reclaim its slot; a later job must still run. On local server startup failure, close the socket and thread, decrement ownership, and raise a useful exception. Never leave child workers or a listener running after runner shutdown or a failed test; use process cleanup in server lifespan and test teardown. Use a fresh job ID per submission, and make repeated outcome polling by the same cursor return the same page without duplication.
