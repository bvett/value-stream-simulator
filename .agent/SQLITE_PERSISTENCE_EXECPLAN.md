## Purpose / Big Picture


A user will be able to finish simulations, stop both services, start them again, and reopen the same inputs, comparisons, charts, and CSV exports. A new installation will include the README walkthrough's completed simulations. Documentation links will open a particular comparison, scenario, and chart without requiring a simulation to run first or any prior browser storage.

SQLite is an embedded database accessed through a local file. Each service will own a different writable database in the user's data directory. The application service owns lasting workspaces and results; the simulation service owns execution jobs and temporarily retained outcomes. The browser continues to use HTTP. Demonstrate the feature with a fresh data directory, a documentation link opened in a fresh browser context, and a service restart that preserves the linked result.

## Surprises & Discoveries


`src/value_stream/app/storage.py` exposes a `WorkspaceStore` protocol, but `get()` and `run()` return shared mutable objects. `src/value_stream/app/coordinator.py` changes `record.status`, individual outcomes, and `record.service_cursor` directly. Merely substituting a SQLite-backed implementation would lose changes. Outcome processing must become an explicit atomic storage operation, meaning all related writes succeed together or none are saved.

`InMemoryWorkspaceStore.prune_history()` and `prune_for_capacity()` delete old unpinned comparisons. That contradicts the new requirement to retain saved data until explicit deletion. Capacity admission must reject new work instead. `AppSettings` currently treats every field as a positive number, and `/api/v1/config` exposes those fields as numeric limits; database paths must therefore use separate configuration.

`RunCoordinator.close()` currently cancels every active upstream job, including jobs in an external service. External application shutdown must detach instead. `ModelScheduler` keeps its queue and subprocesses in memory; the approved scope finalizes interrupted work rather than rebuilding that execution queue.

`src/value_stream/service/app.py` creates a module-level `app`. `src/value_stream/app/contracts.py` constructs both applications to generate OpenAPI. `_LocalService` also constructs a service application before its server starts. Database opening and recovery must happen in the FastAPI lifespan, which is the startup/shutdown context, rather than at import or application construction.

`App.tsx` currently reads only `?workspace=...`, replaces the query string with that one parameter, and derives selected comparisons from the workspace's current task set on each relevant poll. Exact documentation links need independent view state; displaying an older comparison must not change the persisted editor or baseline.

The README describes the default nine-model sweep and an interactive change of maximum developer efficiency to 11. `TaskSetSpec` currently defaults to 500 tasks, depreciation 0.02, task seed 42, uniformly distributed story points from 0.5 to 2, and initial value 1. `ScenarioDefinition` defaults to team sizes 1, 13, and 25 crossed with deployment intervals 0, 5, and 10, team seed 123, and execution seed 456. Existing scenario IDs are derived from definition IDs and settings. Stable definition IDs are therefore essential for sample regeneration.

Inspection found Python 3.11.11, SQLite 3.54.0, and Node 24.21.0 in this workspace. `platformdirs` is installed transitively, but is not a declared application dependency; `filelock` is not installed. No runtime tests or feature prototypes have been run for this planning task.

## Context and Orientation


The Python package uses a `src/` layout and supports Python 3.11 through 3.14 in CI. `src/value_stream/app/server.py:create_app` serves the React studio and workspace API. `app/storage.py` stores workspaces, frozen task sets, run statuses, result references, and reusable results. `app/coordinator.py` submits a run to a simulation gateway and polls outcomes. The gateway in `app/gateway.py` starts a process-local loopback service using `client/web/local_service.py` unless an external URL is configured.

`src/value_stream/service/app.py:create_app` serves job submission, status, outcomes, and cancellation. `service/job_store.py` supplies the `JobStorage` protocol and in-memory implementation. `service/scheduler.py` schedules one subprocess per active model and writes complete outcomes. `service/worker.py:run` validates a worker payload, decodes inputs, executes the engine, and encodes a result. It is the existing simulation path, including execution seeds and result-size checks.

Application and service wire models are Pydantic models in their respective `schemas.py` files. Their `extra="forbid"` setting rejects unknown properties. Persisted data must be upgraded before validation against the current models; relaxing HTTP validation is unnecessary. A payload is a JSON representation of one logical object, such as a task set or an outcome. A payload version describes that JSON shape; a schema version describes the database's tables and columns. Both differ from the existing engine/generator versions, which describe simulation provenance and reusable-result eligibility.

Tests use `unittest` through pytest. `tests/unit/app/test_lifecycle.py` supplies `ControlledGateway`; `tests/unit/app/test_boundaries.py` exercises limits and deletion; integration tests use real FastAPI lifespans and loopback workers. React tests use Vitest, and `app/frontend/e2e/studio.spec.ts` uses Playwright against built assets. Hatchling packages Python, checked-in contracts, and generated frontend assets. `Dockerfile.app` builds the UI and installs the package; `Dockerfile` starts only the simulation service. `.github/workflows/test.yml` runs tests and `.github/workflows/validate.yml` checks contracts, frontend types, and distribution assets.

## Plan of Work


### Milestone 1: establish database ownership, initialization, and compatibility


Create `src/value_stream/service/persistence/` with `config.py`, `database.py`, `migrations.py`, `payloads.py`, `errors.py`, and a minimal `__init__.py` that imports no application-specific code. Use `sqlite3` for SQL and standard `json` for serialization. Promote `platformdirs` to a direct dependency, add `filelock`, and regenerate `uv.lock` with `uv lock`. Use parameterized SQL values and fixed application-owned identifiers. Never deserialize Python objects with pickle, load SQLite extensions, or execute SQL supplied by a database or HTTP request. Include Google-style module, class, and method docstrings for all new production code.

Add a separate `DatabaseConfig` rather than adding path fields to the existing numeric settings dataclasses. Resolve an explicit factory/CLI path first, then the component-specific environment variable, then `<data_dir>/application.sqlite3` or `<data_dir>/simulation.sqlite3`. Resolve `data_dir` from an explicit argument, `VALUE_STREAM_DATA_DIR`, or `platformdirs.user_data_path("value-stream", appauthor=False)`. Paths are filesystem paths, not connection URLs; explicitly supplied missing paths create empty initialized databases without sample data. Defaults alone copy bundled samples when present. Resolve `~` and relative paths once against the caller's working directory. Reject application and owned-local service paths that resolve to the same file.

Acquire a `filelock.FileLock` on `<resolved_database_path>.lock` with zero wait before inspecting, initializing, migrating, or recovering a database, and retain the lock object until close. A second owner fails with `DATABASE_IN_USE` without changing data. Reuse this lock for offline sample import. Do not remove a lock file merely because it exists; the operating-system lock determines ownership. Create new data directories with mode 0700 and database/backup files with mode 0600 where supported, without changing existing user permissions. V1 supports local filesystems and one owner per file.

Use one connection per adapter, `check_same_thread=False`, `isolation_level=None`, and a `threading.RLock` around connection use. Apply connection-local `foreign_keys=ON`, `busy_timeout=5000`, and `trusted_schema=OFF` immediately, including to preflight readers. Set `journal_mode=WAL` and `synchronous=FULL` for writable connections after successful compatibility preflight. WAL is SQLite's auxiliary write-ahead log, which allows readers during writes; it does not make a live main file independently copyable. Use explicit `BEGIN IMMEDIATE`, `COMMIT`, and `ROLLBACK`; never nest write transactions or use `executescript()` inside a transaction, because its implicit commit would invalidate rollback guarantees. Keep network calls, subprocess waits, and `await` outside database locks. Close connections before releasing process ownership.

Identify the database kind in a `store_meta` table and a fixed `PRAGMA application_id`: application `0x56534150`, simulation `0x56534A42`. Use `PRAGMA user_version` for the independently numbered schema version of each kind, starting at 1. `store_meta` holds kind and metadata-format version, not a second competing schema counter. Before enabling write pragmas on an existing file, inspect its kind, version, and integrity with a read-only connection. Reject the other component's database, unsupported future schema or payload versions, malformed JSON, unexpected nonempty unversioned databases, and invalid model data. An existing valid empty SQLite database can be initialized after backup; a zero-byte or non-SQLite existing file is an error. Only absence permits automatic creation. A missing bundled resource permits an empty default; an existing corrupt or incompatible bundled resource is a startup error, not an excuse to use empty data.

For a missing default, copy the closed bundled resource to a uniquely named temporary file in the destination directory, preserve bytes and IDs, verify its manifest hash, kind, integrity, and payload compatibility, flush the file, and atomically publish it while holding the destination lock. Flush the containing directory after publication where supported. For a missing explicit path or absent bundle, build the empty schema in a temporary file and publish only after verification. Clean up only temporary files created by this attempt; never delete a preexisting target. Package resources must be accessed through `importlib.resources`, so installed wheels and source checkouts behave alike.

Before any existing-database schema migration or persisted payload rewrite, create a unique backup beside the database using SQLite's connection backup API, which captures committed WAL content. Verify `integrity_check`, `foreign_key_check`, kind, version, and expected table counts in the backup and record its path. If backup creation or verification fails, stop before migration. Run the complete required migration chain and its version update in one transaction, verify foreign keys and payload conversions before commit, and roll back on any failure. Retain verified backups; do not automatically replace the original from a backup. An operator can close the service, move the damaged file and all its sidecars aside, and restore the verified snapshot. Do not claim two separate databases migrate atomically together.

In `payloads.py`, define a registry keyed by object kind and integer payload version, starting at 1 for workspace editor state, task sets, run metadata, scenario outcomes, job metadata, and results. Serialization uses Pydantic JSON mode and JSON text with nonfinite numbers rejected. Deserialization applies sequential pure dictionary upgrades and then current Pydantic validation. Newly added optional fields with defaults need no database schema change. Renames, removals, or semantic changes require an explicit upgrade and compatibility fixture. If upgrades need to be written back, do that only through the backed-up startup migration path. Do not synthesize new IDs or recompute frozen numerical results during upgrades. Keep old engine/generator provenance; those versions remain part of reuse keys.

Add `tests/unit/service/persistence/test_database.py` and `test_payloads.py`. Prove first-launch exact copying, empty explicit-path creation, missing versus invalid bundle handling, preservation of existing files, kind/version rejection, correct backups with committed WAL data, fault-injected backup/migration failure, rollback of both data and version, process-lock contention, and payload defaults/upgrades. These tests use temporary directories only. A synthetic test migration is sufficient to exercise failure without inventing an artificial public schema version. Run the focused tests before proceeding; acceptance is a reopenable compatible database and unchanged existing data after every injected failure.

### Milestone 2: make workspace changes durable and retain saved comparisons


Keep the `WorkspaceStore` protocol and its in-memory implementation in `src/value_stream/app/storage.py`; put the SQLite implementation in `app/sqlite_storage.py`. Extract storage-neutral mutation helpers only as needed to share actual admission, fingerprinting, outcome-summary, and comparison rules. Do not implement SQLite as an in-memory store periodically dumped to disk. Load workspace summaries and task sets on demand; fetch raw result payloads only when a result, export, or reusable result is requested.

The application schema contains `workspaces`, `task_sets`, `runs`, `run_outcomes`, and `result_blobs`. Use text UUID primary keys for workspaces, task sets, and runs; task sets and runs reference their owning workspace; runs also reference their frozen task set. `workspaces` stores editor revision, created/updated UTC timestamps, input byte count, and versioned editor JSON, excluding task-set and run lists reconstructed from related rows. `task_sets` stores spec/content hashes, byte count, generator provenance, and versioned frozen task/spec JSON. `runs` stores state, request ID/hash, created/updated UTC timestamps, outcome/service cursors, reservation/result byte counts, upstream identity, optional job ID, and versioned request/run metadata excluding outcome and raw-result arrays. Enforce uniqueness of `(workspace_id, request_id)`.

`run_outcomes` uses `(run_id, scenario_index)` as its primary key and enforces uniqueness of `(run_id, scenario_id)` and completed `(run_id, cursor)` values. Store status, nullable result key, and versioned scenario/outcome-summary JSON. A scenario ID can occur in different runs; interactive comparisons already reuse scenario identity, so it must not be globally unique. `result_blobs` uses the existing execution fingerprint as key and stores serialized byte count, payload version, engine/generator provenance, and JSON `ResultData`. Foreign keys protect referenced results; deleting one comparison must not delete a result shared by another. Use indexes for workspace run order, active state, request lookup, result references, and task-set references. Parse/validate results in Python; SQL JSON extensions and SQLite JSONB are unnecessary for V1.

Add explicit operations to the protocol and both adapters: `patch_run(workspace_id, run_id, changes: RunChanges) -> RunRecord`, `complete_outcomes(workspace_id, run_id, outcomes: list[CompletedOutcome], *, service_cursor: int | None = None, terminal_state: RunState | None = None, run_error: ErrorEnvelope | None = None) -> RunRecord`, `active_records() -> list[tuple[UUID, RunRecord]]`, and `close() -> None`. `RunState` is the existing application state type. `RunChanges` is a typed internal patch for state, accepted job ID and upstream identity, cancellation, supersession, retry pause, and error; it distinguishes an omitted error from clearing one. `CompletedOutcome` carries the scenario index, final status, optional result/error, and cache flag. These internal types are not new HTTP request models. Both operations read the latest stored state under their lock, preserving cancellation flags changed while the coordinator awaited HTTP.

Move `complete_outcome`'s summary calculation and terminal cursor allocation into `complete_outcomes`. In one transaction validate indexes and result budgets, insert result blobs/references, update outcome summaries, allocate monotonically increasing application cursors, advance the service cursor, release consumed reservations, and apply terminal state/baseline/latest changes when supplied. Replaying an already committed outcome must not allocate a second cursor or double-count bytes. Validate service cursor order/range and never advance past outcomes not committed. Failed or oversized pages leave the previous checkpoint intact; a subsequent separately committed terminal failure preserves already committed results. Cached completions use the same operation with no service-cursor advance. Existing `finish`/`retain_result` behavior must be consolidated into these operations rather than creating a separate write before the outcome checkpoint.

Refactor coordinator status changes, launch/retry flags, acceptance, cancellation, and supersession to call these operations. Remove reliance on mutable values returned by `get()`/`run()`; both adapters return independent snapshots, and the coordinator uses returned fresh records after mutations. Keep `register`, `save_editor`, comparison changes, and deletion atomic, including revision/admission checks. Retry matching by request ID and hash precedes capacity checks. Use stored UTC epoch timestamps for ordering, expiry, and the persisted interactive cooldown; retain `time.monotonic()` only for in-process retry deadlines. Normalize reused result model indexes for their receiving run without changing numerical content.

Remove automatic saved-run deletion from `prune_history` and `prune_for_capacity` for both adapters. Preserve existing count, pin, input, per-model, per-run, and aggregate-result limits, but change capacity messages to explain explicit deletion or configuration changes. Count durable input bytes, referenced result bytes, and in-flight reservations independently of any bounded in-memory result cache. Reclaim only unreferenced result blobs or temporary caches automatically. Existing data remains readable if a later configuration lowers a limit below current usage; reject additional writes that would increase exceeded usage. Explicit deletion clears relevant baseline/latest pointers and frees only unshared data. Returning to baseline or unpinning does not delete a comparison.

Convert existing lifecycle and boundary tests to use public operations rather than manually editing shared objects. Run a common behavior suite against in-memory and SQLite adapters, recreating the SQLite adapter between write and assertion. Add `tests/unit/app/test_sqlite_storage.py` and `tests/integration/test_persistence_roundtrip.py` for request deduplication, stale revisions, cache reuse, atomic page replay/failure, restart-safe summaries, shared-result deletion, all comparison actions, and full-capacity rejection without deletion. Acceptance is the same result and export after reopen, with no saved comparison disappearing when another run is admitted or rejected.

### Milestone 3: persist jobs and finalize interrupted execution


Implement `SqliteJobStore` in `src/value_stream/service/persistence/job_store.py`, without importing `value_stream.app`. The simulation schema contains `jobs`, `job_models`, and `submissions`. `jobs` stores UUID, job state, model count, result byte count, created/terminal UTC timestamps, last cursor, and versioned metadata. `job_models` uses `(job_id, model_index)`, with state, optional completion cursor, byte count, and nullable versioned outcome JSON. Require unique nonnull `(job_id, cursor)` values. `submissions` maps each submission UUID to its fingerprint and job ID with a cascading foreign key. Create indexes for expiry and active states. Job payloads need not retain complete execution requests because V1 does not resume models after service restart.

Implement existing `JobStorage` operations with transactions. Reservation and idempotent submission lookup are atomic; matching retries precede admission checks and survive restart until job expiry. Starting a model is a conditional queued-to-running transition. Finishing a model atomically writes the result or size error, model state, job counters/state, terminal timestamp, and next cursor. Cancellation writes exactly one cancelled outcome for each unfinished model, preserving completed outcomes. Repeated completion or cancellation is harmless.

Extend `JobStorage` with `interrupt_unfinished() -> None` and `close() -> None`, implemented by both stores. After ownership and migrations succeed, but before accepting requests or starting a scheduler, finalize every persisted queued/running model as failed with `ModelError(code="JOB_INTERRUPTED", model_index=...)`. Preserve all existing completions and append missing outcomes in model-index order with fresh cursors; finalize the job as `completed_with_errors`. Do not launch workers for recovered models. Perform this recovery transaction before applying job TTL pruning, so a nonterminal job cannot remain active indefinitely. Repeating startup must not append outcomes again.

Retain the service's current one-hour terminal-job TTL and count/byte admission defaults using UTC terminal timestamps, independent of application result retention. Expiry deletes submissions with their job. Do not prune active jobs to make room. On graceful service shutdown, stop scheduling new work, mark unfinished jobs interrupted before late callbacks can overwrite those outcomes, terminate/join workers, close the store, and release ownership. Existing user cancellation remains cancelled rather than being rewritten as an interruption. No database lock is held while waiting for workers.

Reuse job-store and real-service contract tests against both adapters. Add restart tests for queued and partially completed jobs, stable completion cursors, concurrent model completions, duplicate completion attempts, cancellation races, expiry across restart, and submission conflicts after restart. Use a subprocess crash test to show committed outcomes survive abrupt process exit and remaining models are finalized on the next start. Acceptance is a terminal, readable job with every model accounted for and no recovered worker launch.

## Idempotence and Recovery


Normal startup and reopening are idempotent: existing data is never replaced by bundled content, completed recovery is not repeated, and compatible current schemas need no backup or write solely to open. Migration versions and payload upgrades are monotonic; successful retries start from the committed version. Failed migrations retain a verified backup and leave the original transaction rolled back. Future-version and corrupt files require a compatible release or explicit operator recovery, never an automatic reset.

Before manual restoration, stop every owner, retain the current database and WAL/SHM files together under diagnostic names, verify the backup, and copy it to the intended path with restrictive permissions. Do not copy only a live main database or restore over running services. Use the application's verified backup API for live snapshots. Keep backup files until the user explicitly removes them; document their disk use.

Sample import acquires exclusive ownership and is explicit, repeatable, and nondestructive to existing records. The builder refuses overwrite so regenerating a release cannot replace a personal database. Temporary test/output paths and named container resources must be task-owned; cleanup never touches the default user directory. New tests restore environment variables, close adapters and HTTP clients, release singleton service references, and stop subprocesses in `finally` blocks even when assertions fail.
